### 下午 — 504 超时链修复

**三层超时同时不足：**
```
浏览器 axios timeout = 120000ms（120s） → 足够
Nginx proxy_read_timeout = 60s          → 不足，60s 先到
Uvicorn 无 --timeout-keep-alive         → 依赖默认（5s?）
```

**修复（三层全部提升至 300s）：**
1. `frontend/src/api/client.ts` → `timeout: 300000`
2. `frontend/nginx.conf` → `proxy_connect_timeout 300s; proxy_send_timeout 300s; proxy_read_timeout 300s`
3. `app/Dockerfile` → `CMD ... --timeout-keep-alive 300`

### 下午 — FastAPI 路由顺序陷阱

**问题：** `GET /api/projects/trash` 返回 404 — `/{project_id}` 路由在 `/trash` 之前，"trash" 被当作 project_id。

**诊断：** `docker compose exec backend python -c "from app.api.v1.endpoints.projects import router; [print(r.methods, r.path) for r in router.routes]"`

**修复：** 将 `/trash` 和 `/clear-trash` 静态路径定义在 `/{project_id}` 动态路径**之前**。

### 下午 — Hard Delete FK 约束失败

**问题：** `DELETE /api/projects/{id}/hard-delete` 返回 500 FK 约束错误 — `approval_logs` 表无 `ON DELETE CASCADE`。

**修复：** 在 `db.delete(project)` 前手动删除子记录：
```python

db.query(DiscardedProject).filter(DiscardedProject.project_id == project_id).delete()
```

## 关键教训

### 教训 1：FastAPI 路由顺序是隐式契约
- 静态路径必须写在路径参数路由之前
- 这是一个"编译时"不会报错、"运行时"才爆炸的陷阱
- 任何新增端点都应该先检查是否与现有 `/{resource}_id` 路由冲突

### 教训 2：三层超时必须同时足够
- 504 问题往往是三层中最短的那层先爆
- 修复一层不够，必须三元组全部提升
- 每次调整都要同步更新 docker-compose.yml / nginx.conf / Dockerfile

### 教训 3：批量删除中的 ORM 对象状态
- 事务回滚后 ORM 对象 detached，访问属性即崩溃
- 防御性做法：在事务外提前捕获 `id` 和 `name`
